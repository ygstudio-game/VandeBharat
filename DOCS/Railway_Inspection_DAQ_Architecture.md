# Railway Inspection Data Acquisition Platform (DAQ)

## Detailed Software Architecture & Engineering Design

> Version: 1.0\
> Target Hardware: NVIDIA DGX + IDS GigE Vision Cameras\
> Objective: Sustain 10 GbE-class ingestion with zero frame loss while
> providing a production-ready acquisition pipeline.

------------------------------------------------------------------------

# 1. Vision

This document defines the complete software architecture for the Data
Acquisition Platform (DAQ). The DAQ begins **after the IDS Peak SDK has
reconstructed a complete frame** from GigE Vision packets. The DAQ is
responsible for:

-   Receiving frames from the SDK
-   Buffering frames safely
-   Writing frames to NVMe SSDs
-   Creating searchable metadata
-   Publishing completed chunks
-   Feeding downstream preprocessing and AI pipelines

## Why the pipeline starts after the SDK

The IDS Peak SDK is responsible for: - GigE Vision packet reassembly -
UDP packet ordering - Missing packet detection - Frame completion -
Camera hardware timestamp extraction - GigE Vision Block ID extraction

The DAQ intentionally does **not** reimplement the GigE Vision protocol.
This reduces complexity, relies on a mature vendor SDK, and isolates
hardware-specific logic to one component.

------------------------------------------------------------------------

# 2. Core Architectural Decisions

## Decision 1 --- Isolate the SDK

Only one service (Receiver) communicates with the SDK.

**Why** - Easy camera vendor replacement - Cleaner architecture -
Hardware-independent downstream services - Simplified testing with
simulators

------------------------------------------------------------------------

## Decision 2 --- Use an Internal Frame Structure

All services exchange one common structure:

``` cpp
FramePacket{
    InternalFrameID
    CameraFrameID
    HardwareTimestamp
    CameraID
    Width
    Height
    PixelFormat
    PayloadPointer
    PayloadSize
}
```

**Why** - Decouples SDK from application - Enables simulator and
production to share code - Stable interface for every service

------------------------------------------------------------------------

## Decision 3 --- Timestamp is NOT the primary key

Each frame has:

-   Internal Frame ID (generated by software)
-   Camera Frame ID (GigE Block ID)
-   Hardware Timestamp

**Why** - Multiple cameras can share identical timestamps - Timestamp
represents capture time, not identity - Camera Frame ID detects missing
frames - Internal ID is stable across the platform

------------------------------------------------------------------------

## Decision 4 --- Chunk Files Instead of Millions of Images

Store:

    Chunk001.bin
    Chunk002.bin

instead of:

    frame0001.png
    frame0002.png

**Why** - Better sequential NVMe performance - Lower filesystem
overhead - Faster indexing - Easier archival

------------------------------------------------------------------------

## Decision 5 --- Metadata in PostgreSQL

Store references only:

-   Chunk ID
-   Offset
-   Timestamp
-   Camera
-   Dimensions

**Why** - Instant random access - No file scanning - Easy SQL queries -
AI pipeline can locate frames quickly

------------------------------------------------------------------------

# 3. Services

## 3.1 Receiver Service

### Responsibility

-   Read completed frame from IDS SDK
-   Validate SDK output
-   Assign Internal Frame ID
-   Convert to FramePacket
-   Push into Ring Buffer

### Does NOT

-   Write disk
-   Run AI
-   Resize images
-   Convert color
-   Call database

### Why

The receiver must never become the bottleneck.

------------------------------------------------------------------------

## 3.2 Ring Buffer

Purpose: Absorb temporary speed differences between acquisition and
storage.

Characteristics:

-   Fixed memory allocation
-   Circular
-   Lock-free (preferred)
-   Producer = Receiver
-   Consumer = Storage

Why:

Storage occasionally pauses.

Receiver must continue accepting frames.

Without a ring buffer:

Receiver waits → SDK buffers fill → dropped frames.

------------------------------------------------------------------------

## 3.3 Storage Writer

Responsibilities

-   Pop FramePacket
-   Append to current chunk
-   Rotate chunks
-   Flush to NVMe
-   Notify Metadata

Writes sequentially for maximum SSD throughput.

------------------------------------------------------------------------

Triggered when a chunk closes.

Publishes

Chunk Ready

-   Preprocessing

-   Backup
-   Cloud Upload

------------------------------------------------------------------------

## 3.6 Preprocessing

Reads completed chunks only.

Operations

-   Bayer conversion (if required)
-   Resize
-   OCR preparation
-   Normalization

Never blocks acquisition.

------------------------------------------------------------------------

## 3.7 AI

Consumes processed frames.

Examples

-   OCR
-   Defect detection
-   Coach number recognition
-   Classification

------------------------------------------------------------------------

## 3.8 Cloud Sync

Uploads

-   Metadata
-   Reports
-   OCR
-   Defects

Raw chunk files remain local.

# 4. Metadata Strategy

Every frame has:

InternalFrameID → Primary software identifier

CameraFrameID → GigE Vision Block ID

HardwareTimestamp → Camera capture time

ChunkID → Storage location

ByteOffset → Exact position inside chunk

This allows deterministic retrieval.

------------------------------------------------------------------------

# 5. Fault Tolerance

The acquisition pipeline must continue operating if:

-   AI fails
-   Cloud upload fails
-   Preprocessing stops
-   Metadata retries
-   Temporary storage delays occur

Only catastrophic storage failure should stop acquisition.

------------------------------------------------------------------------

# 7. Demonstration Strategy

## Goal

Demonstrate sustained 10 GbE-class ingestion.

### Simulator

Implement a FrameSource interface.

Production: Receiver \<- IDS SDK

Development: Receiver \<- Simulator

Everything downstream remains unchanged.

### Dashboard

Display:

-   Throughput (GB/s)
-   Frames Received
-   Frames Written
-   Dropped Frames
-   Ring Buffer %
-   NVMe Write Speed
-   Metadata Count
-   Chunk Count

### Success Criteria

-   Zero dropped frames
-   Sequential NVMe writes sustain target throughput
-   Every frame indexed
-   Every chunk published
-   Receiver never blocks

-   Zero dropped frames
-   Metadata created for every frame
