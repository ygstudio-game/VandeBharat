Section 01

System Overview

VandeInspect AI is a real-time automated railway coach inspection system. It ingests live video streams from inspection-bay cameras, runs two neural networks in parallel (YOLO for defect detection, OCR for coach identification), correlates results into structured inspection findings, persists them to PostgreSQL, and surfaces them through a live WebSocket-connected dashboard.

The system is split into 7 microservices — two GPU-bound Python services, four CPU Python services, one Node.js API, and a React frontend. Services communicate over HTTP (REST) internally and expose a WebSocket endpoint to the frontend for live push events.

ℹ
Two deployment architectures are evaluated in this document Architecture A: GPU services run on a cloud server (RunPod / AWS), frames sent over the internet. Architecture B: All services including GPU inference run on a DGX Spark GB10 at each inspection site. The technical tradeoffs — latency, bandwidth, VRAM, reliability — are quantified in Sections 7–11.

Section 07

Network Bandwidth — Architecture A vs Architecture B

Architecture A — Bandwidth Required to Send Frames to Cloud

Inputs: Camera streams : 4 cameras Frame rate : 25 fps JPEG size/frame : ~50 KB (compressed, 640×640) Calculation per camera: 25 fps × 50 KB = 1,250 KB/s = ~10 Mbps Total for 4 cameras: 4 × 10 Mbps = 40 Mbps sustained upload With overhead (TCP headers, retransmits, HTTPS): ~50–60 Mbps minimum recommended ⚠ Railway inspection sites in remote locations frequently have <10 Mbps uplink. At 10 Mbps, only 1 camera can stream to cloud at 25 fps. 3 cameras must drop frames. Dropped frames = missed detections = inspection gap.

Architecture B — Bandwidth Required (DGX Spark On-Site)

During inspection (all inference runs locally): Camera → Spark: local USB/Ethernet — no internet needed Internet usage : 0 Mbps After inspection (report sync to central server): PDF report size : ~5–10 MB Upload duration : ~10 seconds on 10 Mbps link Timing : Non-real-time — syncs when internet available Model update push (new best.pt from central server): File size : ~140 MB Transfer time : ~2 minutes on 10 Mbps link Timing : Scheduled off-peak — never during inspection

Section 10

Performance Bottlenecks — Where the System Can Be Constrained

BottleneckConditionImpactMitigation
Frame rate vs inference speed Camera outputs 25 fps. YOLO11x on GB10 GPU processes ~5 ms/frame → 200 fps possible. No bottleneck. None — GPU is 8× faster than camera feed rate —
Correlation ThreadPool queue 4 concurrent YOLO calls per ThreadPoolExecutor. If YOLO <5 ms, pool saturates at ~800 frames/s — well above requirement. None under normal load Increase CORRELATION_CONCURRENCY env var if needed
Cloudinary upload latency Each frame uploaded to Cloudinary before correlation. Upload time depends on internet speed. If Cloudinary is slow, frame buffer grows. Correlation waits for URL. Use local MinIO or Backblaze B2 instead of Cloudinary for frame buffer
psycopg2 bulk insert under load execute_values() batches all rows per coach. At 1,000 frames × 5 detections = 5,000 rows per insert. Sub-100 ms for 5K row insert on local NVMe PostgreSQL Already optimal — psycopg2 execute_values is the fastest Python PostgreSQL bulk insert
Frame sampling rate CORRELATION_SAMPLE_N=3 means 1-in-3 frames sent to YOLO. At 25 fps this gives ~8 frames/s per camera to YOLO. A defect present for <0.3 s (3 frames) could theoretically be missed. Adequate for slow train pass-through. Set CORRELATION_SAMPLE_N=1 to process every frame at cost of 3× YOLO load
Network bandwidth (Arch A) 4 cameras at 25 fps at 50 KB/frame = 40 Mbps sustained upload required. On <40 Mbps link, frames must be dropped or compressed further. Missed detections. Arch B eliminates this entirely. Arch A: reduce JPEG quality, increase JPEG compression ratio.
WebSocket broadcast under many clients All dashboard clients connected to /ws receive session events. At 10+ clients, backend fanout increases. Minor CPU increase on Fastify WebSocket handler wsGateway uses room-scoped subscriptions — only clients subscribed to a session receive its events

Technical Recommendation

Hardware Procurement & Deployment Decision

Both architectures run the identical software stack. The Python services, Node.js backend, React frontend, PostgreSQL schema, and Redis queue are unchanged between them. The only difference is where the GPU services run.

Architecture B (DGX Spark) is the correct choice for the following technical reasons, quantified above:

  • 3–8 ms inference latency vs 22–305 ms in Architecture A — GPU co-located with camera input
  • Zero internet bandwidth during inspection vs 40–60 Mbps sustained upload required in Architecture A
  • 11% GPU memory utilisation per train — 89% headroom for load growth, model size increase, or additional cameras
  • 40% GPU compute per train — safe for 2 simultaneous trains (80%) with headroom remaining
  • 72-core ARM64 CPU — all 7 CPU services use <15 cores total; no CPU bottleneck possible
  • 128 GB unified memory — both AI models + all services + OS use ~14 GB; over 8× headroom
  • Docker restart: always — any crashed service self-heals in 5–10 s without human intervention
  • NVIDIA Business Critical SLA — 1-hour Severity 1 response, on-site replacement engineer dispatched
  • Data never leaves the inspection site — all frames processed locally, only reports synced out
