Section 01

What VandeInspect AI Does

VandeInspect AI is an automated railway inspection system. When a train arrives at an inspection site, cameras mounted around the track capture continuous footage of the train's undercarriage, bogies, wheels, and body panels as it passes through. The system processes this footage in real time using artificial intelligence to identify defects — such as cracks, rust, holes, loose components, punctures, or smoke emission — and links every finding to the specific train number and the exact camera position where it was detected. The final output is a structured inspection report that a site engineer can review immediately, replacing the traditional method of manual visual inspection by a human walking alongside the train.

The system is not a single program. It is a collection of seven specialised services, each responsible for one specific task, all working together in a coordinated pipeline. Understanding each of these services — what it does, what it needs, and how it communicates with the others — is essential before evaluating how and where to deploy the system.

Section 02

The Seven Services — What Each One Does

The system is divided into two categories of services: GPU services that require a graphics card to run AI models, and CPU services that handle coordination, storage, reporting, and the user interface. All seven must be running simultaneously for the system to operate correctly.

GPU Service

YOLO Defect Detection

Port 5002

The most compute-intensive service. Runs two AI models simultaneously — one that detects eleven categories of physical defects (rust, crack, leakage, smoke, broken components, deformation, holes, missing parts, punctures, hanging elements, and loose fittings), and a second that locates the bogie region to feed into the OCR pipeline. Requires a CUDA-capable GPU to process frames fast enough for real-time inspection.

GPU Service

OCR — Train Number Reader

Port 5000

Uses RapidOCR with ONNX Runtime to read the train number printed on the bogie. Every defect detected must be linked to a train number — without this service, the system cannot tell which train has the defect. Runs on the same GPU as YOLO but as an independent service so either can be updated or restarted without affecting the other.

CPU Service

Frame Extractor

Port 5003

The entry point of the pipeline. Connects to the cameras, reads the incoming video stream, and cuts it into individual frames at the required rate. Sends each frame to the YOLO and OCR services via HTTP. Does not use the GPU — pure CPU and network I/O work.

CPU Service

Correlation Engine

Port 5005

Receives the defect results from YOLO and the train number from OCR and merges them into a single, coherent record — this defect, on this train, at this camera position, at this timestamp. Without correlation, you have two separate streams of data with no connection between them.

CPU Service

Sync Engine

Port 5004

Takes the correlated inspection records and writes them to the database. Also handles synchronisation logic — ensuring data is not duplicated if a network interruption occurs mid-write. Acts as the pipeline's final data store before reporting.

CPU Service

Report Generator

Port 5006

Queries the database for completed inspection sessions and assembles structured reports — listing all defects found, their severity scores, the train number, camera source, and timestamps. Reports are available immediately after a train passes through.

Backend + Frontend

Backend API & Operator Dashboard

Backend: 8001  |  Frontend: 5173

The backend is a Fastify (Node.js) API server that exposes inspection data to the frontend and handles authentication, camera health monitoring, and session management. The frontend is a Next.js web application that site engineers open in a browser to review live detections, historical reports, and camera status. Together they form the human-facing layer of the entire system.

Section 03

How the Services Talk to Each Other

All seven services communicate over HTTP — the same protocol a browser uses to load a website. When the frame extractor has a new camera frame ready, it sends an HTTP POST request to the YOLO service at port 5002 and another to the OCR service at port 5000, both at the same time. Both services process the frame independently using the GPU and send their results back. The correlation engine then receives both sets of results, merges them, and passes the final record to the sync engine for database storage. The backend service queries the database continuously and serves the data to the frontend dashboard.

Crucially, all of this communication happens internally — no frame, no result, and no detection record leaves the machine during the inspection process. The services talk to each other the same way people in the same office talk across a desk, not the way remote teams communicate over email.

Why seven separate services instead of one program? Each service can be updated, restarted, or replaced independently without stopping the others. If a new AI model is ready, only the YOLO service restarts — the rest of the pipeline keeps running. If the report generator has a bug fix, deploying it does not interrupt live camera processing. This design is what makes the system maintainable at scale across many inspection sites.
Section 04

What You Need to Host This Successfully

Beyond the seven services themselves, a successful deployment requires a supporting infrastructure layer. These are the components that keep the system running reliably, allow it to be managed remotely, and enable the self-improving AI pipeline.

At Every Inspection Site

  • Primary compute unit — the machine that runs all seven services. Either a Custom PC with a discrete GPU or a DGX Spark. This is the most critical hardware decision and is covered in detail in Sections 05 and 06.
  • Cameras — industrial cameras mounted at fixed positions around the track, calibrated to capture every side of the train as it passes. The system currently supports USB and GigE camera interfaces.
  • AI model weight files — two trained model files (best.pt for defect detection, train_num_detector.pt for bogie localisation) must be placed on the compute unit before the system can run. These files are not included in the codebase and must be trained and deployed separately.
  • Network connection — required for syncing reports to the central server and for receiving model updates. Not required for the inference pipeline itself, which runs fully locally.
  • Stable power supply — both deployment options draw continuous power during operation. An uninterruptible power supply (UPS) is recommended to handle power fluctuations at rail site locations.

Central Server (One, Shared Across All Sites)

  • VPS or dedicated server — a Linux server (minimum 4 CPU cores, 8GB RAM, 1TB SSD) that acts as the coordination hub. Collects flagged frames from all sites, hosts the labeling interface, stores the growing dataset, and pushes updated models to all Spark units simultaneously.
  • PostgreSQL database replica — aggregates inspection records from all sites for central reporting and management visibility.
  • Dataset storage — at least 1TB of accessible storage for the labeled image dataset that grows over time. Can be hosted on the central server itself or on an object storage provider such as Cloudflare R2.

Cloud GPU — For Model Training Only

  • GPU compute provider — RunPod (recommended), Lightning AI, or AWS. Used exclusively for retraining the AI model when new labeled data is available. The cloud GPU is not involved in day-to-day inspection — it is spun up, used for 4–6 hours of training, then shut down. Cost is approximately ₹1,300–1,500 per training run on RunPod using 2× H100 GPUs.
  • Training pipeline automation — a script on the central server that triggers the cloud GPU instance, uploads the latest dataset, monitors training progress, saves the resulting model, and notifies all inspection sites to pull the update.

Labeling Workflow

  • Human labelers — when the YOLO service encounters a frame it is not confident about, that frame is flagged and sent to the central server. A human reviews it, confirms or corrects the detection, and it joins the labeled dataset. Over time this dataset grows and model retraining produces a more accurate model.
  • Labeling interface — a web tool (such as Label Studio or a custom interface) hosted on the central server where labelers review and annotate flagged frames.
⚠
Model files are mandatory before first deployment. The system launches successfully and serves API responses even without model files, but the YOLO service returns HTTP 503 (service unavailable) for every inference request until the .pt files are placed in the correct directory. Deployment planning must account for model training before the first site goes live.
Section 05

Deployment Strategy A — Custom PC with Discrete GPU

Custom PC (Intel Core Ultra 9 285K + RTX PRO 6000 Blackwell / RTX 5090)

Windows x86_64  |  Discrete GPU  |  All services on one machine  |  Cloud GPU for training

In this strategy, a high-specification custom PC is placed at each inspection site. The machine runs Windows, and all seven services start automatically using the existing batch scripts (run.bat). The discrete GPU — either the consumer-grade RTX 5090 (32GB VRAM) or the enterprise-certified RTX PRO 6000 Blackwell (96GB VRAM) — handles all YOLO and OCR inference. Services communicate over localhost, and inspection data is written to either a local PostgreSQL instance or a cloud-hosted Neon PostgreSQL database.

How Training Works in This Strategy

Model training does not happen on the site PC. When enough new labeled frames have accumulated on the central server, a RunPod cloud GPU instance (2× H100) is started remotely. The dataset is uploaded, YOLO11x is trained from the base weights over 300 epochs (approximately 4 hours), and the resulting best.pt file is downloaded back to the central server. A deployment script then pushes the new model file to every site PC and restarts the YOLO service on each one.

Section 06

Deployment Strategy B — NVIDIA DGX Spark

NVIDIA DGX Spark (GB10 Grace Blackwell Superchip)

Ubuntu ARM64  |  Unified GPU+CPU memory  |  Docker Compose  |  Cloud GPU for training

In this strategy, an NVIDIA DGX Spark unit is placed at each inspection site instead of a custom PC. The Spark is roughly the size of a hardcover book and runs Ubuntu Linux on NVIDIA's own GB10 Grace Blackwell Superchip — a single chip that combines an ARM64 CPU and a Blackwell GPU sharing 128GB of unified memory. All seven services run inside Docker containers managed by Docker Compose. The Spark was designed specifically for always-on AI workloads and is validated for continuous 24/7 operation with no thermal throttling under sustained load.

Because the CPU and GPU share the same 128GB memory pool, there is no PCIe bottleneck between them. A frame prepared by the CPU is handed directly to the GPU without any memory copy operation, which is meaningfully faster for the continuous frame-by-frame processing this system requires. NVIDIA provides first-class ARM64 builds of PyTorch, CUDA, and cuDNN specifically for the DGX Spark, so the transition from the current x86 codebase is a matter of Dockerfile changes rather than application code changes.

Why Docker on the Spark Makes This Cleaner Than Strategy A

In Strategy A, all services run as raw Python processes managed by a batch file. If one crashes, the others keep running but the pipeline is broken. In Strategy B, Docker Compose manages every service as an isolated container with an automatic restart policy. If the YOLO container crashes, Docker restarts it within seconds without any human intervention and without affecting the other six containers. The entire system starts with a single command and behaves identically on every Spark unit across every site.

Section 08

Recommendation

Both strategies use identical cloud GPU infrastructure for training and an identical central server for coordination. The only meaningful difference is what sits at the inspection site. Over a three-year deployment lifecycle, the DGX Spark costs less than half per site, uses one-third of the power, delivers better data security, and is backed by an enterprise support contract with defined SLAs — at the cost of two weeks of porting work upfront.

Choose Strategy A (Custom PC) if

  • The project must go live in days, not weeks
  • The team has limited Linux or Docker experience
  • Budget per site is flexible and maximising raw GPU performance is the priority
  • The client is comfortable with inspection data in a cloud database

Choose Strategy B (DGX Spark) if

  • Data must never leave the inspection site
  • Power efficiency and cabinet space are constrained at sites
  • A single vendor support contract is required for compliance
  • Long-term cost across many sites is the primary budget concern
  • The team has 2 weeks to port the deployment to Docker

In both strategies, model training is handled by RunPod 2× H100 cloud GPUs at approximately ₹1,300 per training run. The central server is identical. The self-learning pipeline is identical. The only decision to make is which machine sits at the inspection site — and for a production, safety-critical, multi-site railway deployment, the DGX Spark is the more durable, secure, and cost-efficient choice over the full deployment lifetime.
