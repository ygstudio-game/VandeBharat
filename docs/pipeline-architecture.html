Architecture reference · frame pipeline

From sequential batch to fan-out inspection pipeline

How frames move from camera to defect record today, where that breaks under 24/7 operation, and the fan-out design that scales cleanly from two models to four — OCR, Component, Defect, Underbogie.

Scope Framing · preprocessing · model orchestration · synchronization Status Current-state audit + proposal Updated 2026-07-10

00Overview

Two pipelines exist in the codebase today. The production path is upload-driven: a full video file is dropped in, sampled at a fixed frame rate, and pushed through OCR → Sync → Correlation as a strict sequential chain. A second, more capable ingestion path — motion-triggered capture, frame quality gating, stream reconnect, backpressure buffering — already exists in services/ingestion/ but isn't wired into the production flow. Nothing consumes what it publishes.

The proposal below keeps the parts that work (Redis Streams with consumer groups, the watchdog, the correlation fusion logic) and replaces the two things that won't survive a jump from 2 models to 4 and from "upload a file" to "run unattended, forever": fixed-fps sampling, and a sequential stage chain where every new model tacks more latency onto the end.

01Current pipeline

Everything downstream of upload runs as one strict chain — each stage waits for the previous one to fully finish before it starts.

Framing

Session create POSTs the uploaded file to the Frame Extractor, which opens it with cv2.VideoCapture and keeps every Nth frame, where N = video_fps / desired_fps (default 1 fps). No motion trigger, no ROI gating, no dedup — a straight fixed-interval sample of a file that's already fully recorded.

Preprocessing

ROI crop with 15% padding ahead of OCR; a fallback pass runs grayscale → 2× upscale → sharpen kernel → CLAHE → Gaussian blur when the raw crop doesn't read cleanly. Frames are re-encoded to JPEG at quality 85. No blur/brightness quality gate and no dedup exist on this path — both are implemented, but only in the unused ingestion service.

Model orchestration

OCR runs bogie-ROI detection through YOLO, crops, then tries PaddleOCR raw → PaddleOCR preprocessed → full-frame preprocessed, one frame per HTTP call, batched 4-concurrent at the backend. Sync clusters YOLO "gap" detections into coach boundaries and assigns every frame to a coach by trigger-id range. Correlation samples every 3rd frame, fans out to the YOLO defect model across a 4-worker thread pool, then runs Bayesian fusion + voting to dedupe overlapping detections into defect_events.

Synchronization

Every frame gets a monotonic trigger_id and camera_id at extraction. Everything downstream — which coach a frame belongs to, which detections match which train — is resolved by joining these back against Postgres. The Redis Stream messages that move work between stages carry only session_id (and coach_id once known); frame identity itself isn't carried in the queue payload.

04Proposed architecture

Two changes carry the whole redesign: trigger the capture off physical distance instead of a clock, and replace the sequential chain with a frame bus that every model reads from independently.

Distance-triggered framing

Trigger capture from an axle counter, wheel encoder, or IR break-beam per bogie pass — the pattern used in production rail-inspection rigs — instead of a fixed frame rate. Frame density per bogie stays constant regardless of train speed. Where no hardware trigger is available yet, fall back to the motion-score state machine already built in services/ingestion/scheduler.py.

Frame bus, not a stage chain

One capture event publishes one frame envelope to a Redis Stream. OCR, Component, Defect, and Underbogie each read that stream as their own consumer group, entirely independent of each other's pace. An aggregator joins results back together by frame id once all four have reported, or times out and flags whichever modality didn't. Adding a fifth model later means adding a fifth consumer group — the bus doesn't change.

Frame identity travels with the message

Every envelope carries { session_id, camera_id, frame_number, trigger_id, timestamp, coach_id_if_known }. Correlation becomes an in-memory join on that envelope, not a Postgres lookup — it keeps working even if the database is temporarily behind.

Underbogie as its own trigger domain

The underbogie camera sits at a different mount and angle (pit-mounted, looking up) and fires on its own timing relative to the axle sensor. Give it its own camera_id and trigger stream, and join it to the same coach_id downstream by timestamp window — don't force it into the side-camera trigger-id scheme.

Batch inside each model server

With four models sharing GPU budget instead of two, batch a small time-window of frames per inference call (4–8) rather than one frame per HTTP request. Throughput per model rises well past linear at batch sizes above 1 on the same hardware.

06Target camera topology — 7-camera design

The concrete rig this system is being built for: 1 top OCR camera, 4 bottom component cameras tiled into one composite, 2 bottom underbogie cameras, all genlocked. Confirmed design choices below.

Confirmed — tiling is a fixed grid composite (4 cams cover distinct fixed regions, no feature-matching/homography needed). Defect detection is split into two specialized models — Component-Defect and Underbogie-Defect — each re-scanning its own domain's full annotated frame(s), not per-detection crops. 08Architect's clean-slate design — Framing, Preprocessing, Synchronization

Written as if starting today, ignoring the existing codebase entirely. Scoped to only the three concerns asked for: how frames get captured, what happens to them before any model sees them, and how everything stays aligned across 7 genlocked cameras. It builds directly on the confirmed topology (§06) and defect taxonomy (§07) — the model-orchestration fan-out from §04–05 still stands, this replaces and deepens only the framing/preprocessing/sync layers underneath it.

The one decision that changes everything else — your input is genlocked mp4 files, one complete recording per camera per train pass, not a live per-frame socket. That means synchronization is a batch manifest-building problem, not a live-stream timeout/join problem. Everything below is designed around that fact. If a future phase moves to true live per-frame RTSP ingestion (e.g. for mid-pass alerting before the train clears the yard), the §04–05 live fan-out design becomes relevant again — the two are not the same problem and don't share a solution.

1. Framing

Framing here isn't "pick a frame rate" — it's three different extraction policies driven by what each camera physically has to cover, all reconciled against a shared genlock clock, with explicit accounting for dropped frames instead of assuming the hardware never fails.

3 lanes run identically in shape, differ only in the amber extraction-policy box · shared genlock clock means the barrier only waits on ledger completeness, not on cross-camera agreement.

Framing policy per camera role
RoleExtraction policyWhy

2. Preprocessing — full task breakdown per camera role

Three stages apply to every frame regardless of source, then each camera role gets its own specialized chain. The two things most likely to get skipped in a first build — geometric calibration and low-light handling — are exactly the two the MVIS spec's measurement-based defects (buffer height in mm, wheel shelling depth in mm) depend on. Skip either and those specific defect classes can't be certified against spec, not just "less accurate."

Crit dashed box = a physics limit, not an engineering gap — no amount of 2D preprocessing recovers sub-mm depth. Warn = flagged but non-blocking. Trunk above the fork is the only preprocessing shared by all 7 cameras.

3. Synchronization

Because the whole file is available before processing starts, sync doesn't need to guess. It builds one deterministic manifest per coach, once, and every downstream model reads from that — not from a live join with a timeout.

Coach boundary correction — coach assignment isn't a generic "presence signal." The OCR camera detects the physical gap between two coaches directly and timestamps it; everything captured between two consecutive gap timestamps belongs to whichever coach number was OCR-read in that same window. Full mechanism, edge cases, and the resulting Train → Coach → Components (Undercarriage + Bottom) dashboard hierarchy are elaborated in the standalone Framing/Preprocessing/Synchronization doc.

Warn dashed = the two places this design admits it could be wrong (genlock drift, camera gaps) and handles explicitly instead of assuming away.

09More approaches worth evaluating

Beyond the core fan-out proposal — options to reach for as camera count, model count, or uptime requirements grow past what the base design covers.

Framing

Alternative / supplementary capture strategies
ApproachMechanismTradeoff
Line-scan camera Continuous 1D sensor builds the 2D image as the bogie passes — removes the framing/triggering question entirely. Standard in rail NDT rigs, strongest fit for Underbogie. Dedicated hardware; capture rate must sync to belt/axle speed, not a generic camera driver.
Pre-trigger ring buffer Circular buffer holds the last N seconds continuously; a trigger pulls frames from before and after the event, not just after. Catches defects that occur just before the sensor fires. Costs per-camera memory/storage headroom.
Speed-adaptive frame rate Derive fps from a tachometer/GPS speed feed when no discrete axle trigger exists — smoother than motion-score, cheaper than a physical encoder. Still coarser than a true distance trigger; needs a speed signal available.
Redundant dual-camera per checkpoint Two cameras cover the same physical point; if one drops a frame or fails, the other covers it. Doubles camera cost and bandwidth at that checkpoint.

Preprocessing

Beyond crop + CLAHE fallback
ApproachMechanismTradeoff
GPU-resident preprocessing Resize/crop/normalize via CUDA/DALI/nvJPEG instead of CPU OpenCV — removes the CPU↔GPU transfer bottleneck once 4 models are pulling frames instead of 2. More moving parts in the inference container; worth it once GPU sits idle waiting on CPU preproc.
Per-camera calibration profile One-time homography/perspective correction per camera mount, stored as config, applied at preprocessing — every model sees consistent geometry regardless of install angle or height. One-time calibration pass per camera install; pays off every frame after.
Perceptual-hash dedup phash/dhash on frames that already passed the blur/brightness gate — catches near-duplicate consecutive frames the quality gate lets through. Needs a hash-distance threshold tuned per camera; cuts redundant GPU work further.
Multi-frame fusion for low-confidence OCR When single-frame OCR confidence is low, combine 3–5 consecutive crops of the same plate (majority vote / super-resolution) instead of one preprocessed retry. Extra latency only on the low-confidence path — the common path is untouched.
Day/night preprocessing branch Separate normalization for IR/low-light frames vs. daylight, selected by an ambient-light or histogram check. Two preprocessing code paths to maintain instead of one.

Synchronization

Beyond trigger_id + envelope join
ApproachMechanismTradeoff
PTP clock sync across camera nodes Sub-millisecond synchronized timestamps across every capture node (PTP hardware, or chrony as a software fallback) — matters once Underbogie's independent trigger domain has to line up with the side cameras by timestamp. Needs PTP-capable NICs/switches, or accepts looser sync via software fallback.
Central sequencer assigns coach_id at capture time A master controller stamps coach_id into every frame envelope as it's captured and broadcasts it to all camera nodes — instead of the sync engine reconstructing coach boundaries after the fact via gap-clustering. Removes gap-detection fragility outright; needs one authoritative sequencer upstream of ingestion.
Watermark-based "coach closed" signal Borrow the event-time watermark pattern from stream processing (Kafka Streams / Flink) — the aggregator gets an explicit "no more frames for coach N" signal instead of inferring closure from a timeout. The watermark emitter has to track the physical bogie-passed signal, not just wall-clock time.
OCR-number cross-check as standing reconciliation The OCR-number vote already exists in sync_engine as a fallback when gap detection fails entirely — promote it to run alongside trigger-id correlation on every coach and flag mismatches. One extra comparison per coach — cheap next to what a silent mis-sync would cost.
Idempotency key per frame envelope Redis Streams retries can redeliver a message; a stable id per envelope lets consumers and the aggregator dedupe safely instead of double-processing on retry. Small bookkeeping cost per consumer group.

10Migration path

Ordered by dependency — each step unblocks the next.

  1. Wire the ingestion service into production. Point session creation at services/ingestion/ instead of the bare frame_extractor capture loop — this alone brings in reconnect, quality gate, and backpressure buffering that already exist and are tested.
  2. Add frame identity to every queue message. Extend the Redis Stream payload schema to carry the full envelope, not just session_id. Do this before splitting models — it's the foundation the fan-out depends on.
  3. Split OCR and Component+Defect into independent consumer groups on the same stream, proving the fan-out pattern with the two models you already have before adding new ones.
  4. Stand up the aggregator as a join-by-frame_id service with a timeout/partial-result path, replacing the current sequential "sync then correlate" hand-off.
  5. Introduce distance-based triggering. If axle/encoder hardware isn't ready yet, switch to the motion-score scheduler from services/ingestion/scheduler.py as an interim step — it's a strict upgrade over fixed-fps either way.
  6. Add Component, Defect, and Underbogie as new consumer groups once the bus and aggregator are proven under the first two models. Underbogie gets its own camera_id and trigger stream from day one.
  7. Default the watchdog and circuit breaker on, and extend the breaker to wrap the camera/RTSP source — this should land before the system runs unattended, not after.
