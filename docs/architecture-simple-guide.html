Section 01

What the System Does

  • A train arrives at an inspection site and slowly moves through a set of cameras mounted around the track
  • Cameras capture continuous video of the train — undercarriage, bogies, wheels, body panels — as it passes
  • The system reads that video in real time and uses AI to find problems: cracks, rust, holes, loose components, missing parts, or smoke
  • At the same time it reads the train number printed on the bogie so every defect is linked to the correct train
  • A site engineer gets a full inspection report the moment the train clears the station — no manual walk-around needed
ℹ
Why does this system need both a CPU and a GPU? Reading camera feeds, moving data between services, writing to a database, and generating reports are all general computing tasks — a CPU handles them perfectly well. But examining millions of pixels per frame to detect a defect requires running a neural network, which a GPU does 50–100× faster than a CPU. Both are needed, doing completely different jobs.
Section 02

The Seven Services — What Each One Does

The system runs as seven smaller services, each with one specific responsibility. They run simultaneously and pass data to each other. This means if one needs to be updated or restarted, the other six keep running.

GPU Services — Require the Graphics Card

GPU Required

YOLO — Defect Detection Model

Port 5002

The AI brain of the system. Runs two models simultaneously — one that scans every frame for defects and one that locates the bogie region for the OCR service.

  • Detects 11 defect types: rust, crack, hole, leakage, smoke, loose parts, missing parts, deformation, puncture, broken, hanging
  • Returns: defect type, exact position in the image, severity score
  • Needs GPU — processes millions of pixels multiple times per second
GPU Required

OCR — Train Number Reader

Port 5000

Reads the train number printed on the bogie. Without this, the system knows a defect exists but cannot link it to a specific train.

  • Receives the cropped bogie region identified by YOLO
  • Returns the train number as readable text
  • Needs GPU for fast, accurate text recognition in varied lighting

The Most Important Service — Where It All Comes Together

Core Business Logic

Correlation Engine — Where Defect Detection Becomes a Finding

Port 5005  |  CPU Service

YOLO says: "There is rust at this position in this frame."
OCR says: "This frame belongs to Train 12345."
The Correlation Engine says: "Train 12345 has rust on its front-left bogie, detected by Camera 2 at 14:32:07."

  • Takes defect data from YOLO and train number from OCR and links them into one complete inspection finding
  • Tags every finding with: which train, which camera, which component, exact timestamp
  • This is where raw AI output becomes an actionable, reportable inspection result
  • Without this service, you have two separate streams of unconnected data — defects without train IDs, train IDs without defect details
  • Runs entirely on CPU — no AI model, just intelligent data matching and linking

CPU Services — Handle Everything Else

CPU Only

Frame Extractor

Port 5003

The entry point. Connects to all cameras, reads the video stream, cuts it into individual frames, and sends each frame to YOLO and OCR at the correct rate.

CPU Only

Sync Engine

Port 5004

Receives completed inspection findings from the Correlation Engine and writes them safely to the database. Handles retries if a write fails so no finding is ever lost.

CPU Only

Report Generator

Port 5006

Reads completed inspection sessions from the database and assembles formal reports listing all defects, severity scores, train numbers, and camera positions.

Backend + Frontend

Backend API & Engineer Dashboard

API: Port 8001  |  Dashboard: Port 5173

The backend serves all inspection data through an API. The frontend is the web interface engineers open in a browser to see live detections, camera health, and historical reports in real time.

Section 03

Architecture A — AI Detection Runs on Cloud GPU

The Detection Model Lives in the Cloud

Camera frames travel from the inspection site over the internet to a cloud GPU, which runs YOLO and OCR, then sends results back

What This Architecture Looks Like

  • Cameras are mounted at the inspection site as normal
  • A lightweight edge PC sits at the site — its only job is to capture frames from cameras and send them out
  • The edge PC does not run YOLO or OCR — it has no GPU required for inference
  • Every captured frame is compressed and sent over the internet to a cloud GPU server (AWS, RunPod, or similar)
  • The cloud GPU server runs the YOLO defect detection and OCR train number reading
  • Results (defect type, position, train number) are sent back to the site over the internet
  • The Correlation Engine, database, and dashboard run either on the edge PC or on a central server
  • One cloud GPU server can theoretically serve multiple inspection sites simultaneously

Why This Architecture Exists — The Reasoning

  • No expensive GPU hardware at every site — the edge PC can be a cheap machine with no GPU. The GPU lives in the cloud and is shared
  • Centrally managed — model updates happen on the cloud server once and all sites get the new model automatically
  • Scales horizontally — one bigger cloud GPU can serve 5 or 10 sites at once without putting hardware at each location
  • No hardware maintenance at remote sites — if the cloud GPU fails, you spin up a new one in minutes

Weaknesses of This Architecture

  • Internet is mandatory during inspection — if the connection drops even briefly, frames are lost and detections are missed for that window. A missed crack on a bogie is a safety risk
  • Network latency adds up — sending a frame to the cloud and getting a result back takes 20–300ms depending on connection quality. At 25 frames per second per camera, this creates a processing bottleneck and frames must be queued or dropped
  • Bandwidth is heavy — sending 4 camera streams of compressed video to the cloud continuously requires a fast, stable internet connection at the inspection site. Many rail sites in remote locations do not have this
  • Sensitive data leaves the site — every camera frame of railway infrastructure is sent to a third-party cloud server over the internet
  • Ongoing cloud GPU cost — unlike training which runs for a few hours a year, inference is continuous. A 24/7 cloud GPU for live inspection costs significantly more over time
  • Single point of failure is outside your control — if the cloud provider has an outage, your inspection system stops working and you cannot fix it yourself
Section 04

Architecture B — AI Detection Runs On-Site with DGX Spark

The Detection Model Lives at the Inspection Site

The DGX Spark at each site runs YOLO, OCR, and all seven services locally — nothing is sent to the cloud during inspection

What This Architecture Looks Like

  • Cameras are mounted at the inspection site as normal
  • One DGX Spark unit sits at each site — roughly the size of a large hardcover book, fits in any standard cabinet
  • All seven services run inside Docker containers directly on the Spark
  • The Spark's built-in GPU runs YOLO and OCR on every camera frame without any internet connection
  • The Correlation Engine, database, and report generator also run on the Spark — everything is self-contained
  • Nothing leaves the site during inspection — frames, detections, and reports are all stored locally
  • Only finished inspection reports are optionally synced to a central dashboard when internet is available
  • For model training — a cloud GPU (RunPod) is rented on demand, used for 4–6 hours, then shut off. Training is completely separate from inference

Why This Architecture Exists — The Reasoning

  • Zero latency for inference — the GPU is in the same box as the cameras. Processing happens in 2–5ms per frame. No network round trip ever
  • Works without internet — the inspection never stops because of a network issue. The system is fully self-sufficient
  • Data stays on-site — railway infrastructure inspection footage is sensitive data. It never leaves the inspection site
  • Each site is independent — if one site's Spark has an issue, the other sites keep running. There is no shared central point of failure
  • Training is separate and cheap — the cloud GPU is only used for periodic model retraining, not live inference. Training costs approximately ₹1,300 per run and runs a few times a year

How Model Training Works (Separate from Inspection)

Training the AI model is completely separate from running the inspection. The DGX Spark never trains — it only does inference. Training happens on a cloud GPU on demand.

Section 06

Why the DGX Spark Is the Right Choice — And Why It Will Not Fail

Railway inspection is safety-critical. A missed defect has real consequences. The hardware running this system must work every single time, without depending on external conditions like internet connectivity or cloud provider availability. Here is exactly why the DGX Spark meets those requirements.

Built Specifically for Always-On AI Workloads

NVIDIA designed the DGX Spark and markets it specifically for "always-on agent workloads" — meaning continuous AI inference running 24 hours a day, every day. This is not a secondary use case. It is the primary use case the hardware was built for.

Zero Thermal Throttling — Independently Tested

Independent labs ran the Spark at full AI inference load continuously and recorded zero thermal throttling. The external power supply design keeps heat-generating components outside the chassis, giving the GPU far more thermal headroom than any desktop PC running a discrete GPU.

Proven in Real-World Continuous Operation

Real-world users have documented running the Spark at full AI workload for 9 consecutive days without any thermal issue or performance drop. This is documented evidence, not a marketing claim.

Only 40% GPU Used Per Train — Massive Headroom

Processing one train with 4 cameras uses approximately 40% of the Spark's GPU capacity. The remaining 60% sits idle. The system has enormous headroom — even if camera count doubles to 8, the GPU is at 80% with headroom remaining.

128GB Memory — Never Runs Out

Both AI models, all seven services, the local database, and the operating system together use approximately 12–15GB. The Spark has 128GB. There is more than 8 times the required memory available. The system will never slow down or crash because of memory pressure.

Docker Auto-Recovery — Self-Healing System

Docker's restart policy means if any service crashes for any reason, Docker detects it and restarts it in seconds — automatically, without any human intervention, without affecting the other six services. The inspection continues without an engineer needing to do anything.

No Dependency on Internet or Cloud

Unlike Architecture A where every inspection depends on a working internet connection to a cloud GPU, the Spark runs entirely independently. There is no external dependency that can cause an inspection failure. It works with power alone.

NVIDIA Business Critical Support

If the hardware itself fails completely, NVIDIA's Business Critical support tier commits to a 1-hour response for Severity 1 (complete system down) and dispatches onsite engineers for replacement. This is a defined contractual commitment, not a consumer helpline.

Final Position

The Bottom Line

The fundamental question is: should the AI model that detects railway defects run on a remote cloud server reached over the internet, or on a dedicated machine sitting at the inspection site?

For a safety-critical inspection system deployed at railway sites — including remote locations where internet connectivity may be limited — the answer is clear. The detection must happen locally. Every millisecond of network latency, every brief internet outage, every cloud provider downtime event becomes a gap in inspection coverage. No gap in a railway inspection system is acceptable.

The DGX Spark is the right choice because

  • Inspection works with power alone — no internet, no cloud dependency, no third-party availability required
  • Sub-5ms inference latency — frames are processed as fast as the camera produces them, with no network round trip
  • Purpose-built hardware — designed and validated for exactly this type of continuous 24/7 AI workload
  • Self-healing through Docker — crashed services restart in seconds without human intervention
  • All data stays at the site — railway infrastructure data never travels to a third-party cloud server
  • Enterprise support with defined SLAs — NVIDIA responds in 1 hour for a complete system failure
  • Training remains cloud-based and cheap — the cloud GPU is used only for periodic model improvement, not live inspection
